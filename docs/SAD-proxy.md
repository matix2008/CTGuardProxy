# COPYTRUST — защищённое взаимодействие с copytrust-svc

**SAD, версия 0.5** | 19.11.2026

Целевая архитектура и поэтапное внедрение. Открытые вопросы обозначены идентификаторами Q-xx и собраны в разделе 6. Значения параметров и варианты реализации, для которых требуется решение, не являются установленными требованиями. Этап может начаться после закрытия относящихся к нему вопросов, необходимых для развёртывания; вопросы последующих этапов не блокируют срочный переход на HTTPS.

## 1. Назначение и архитектура

### 1.1. Цели

Решение предназначено для обеспечения доступности сайта COPYTRUST при отказах `copytrust-svc` и для защиты межсервисного взаимодействия:

- Ограничить время ожидания SOAP-ответов и предотвратить каскадный отказ сайта при недоступности `copytrust-svc` или сетевого канала.
- Обеспечить конфиденциальность и целостность данных посредством TLS на всех межсерверных участках, с проверкой сертификатов и имён узлов.
- Централизовать аутентификацию 2–5 клиентских приложений на VPS-proxy с помощью индивидуальных клиентских сертификатов (mTLS).
- Сохранить идентификацию клиентов и действующие правила доступа к операциям `copytrust-svc`.
- Закрыть прямые вызовы API `copytrust-svc` в обход VPS-proxy.
- Минимизировать количество инфраструктурных компонентов: HAProxy, штатные механизмы Windows и PHP, локальные файлы конфигурации и сертификатов. Vault, отдельный сервер PKI, внешняя система мониторинга и автоматическое переключение сайта в режим «Ремонт» не входят в решение.

### 1.2. Исходное состояние

17.11.2026 сайт COPYTRUST перестал своевременно отвечать на HTTP-запросы. Apache 2.4.41, MPM `prefork`, `MaxRequestWorkers = 20`; после перезапуска лимит рабочих процессов был достигнут повторно за 74 секунды. Синхронное ожидание SOAP-ответов создаёт риск исчерпания рабочих процессов Apache при отказе сервиса или сетевого канала. Архитектура должна исключать длительное ожидание новых вызовов после обнаружения отказа. Существующий SOAP-тайм-аут — 30 секунд. Дополнительный риск — передача Basic Auth и SOAP-данных по нешифрованному HTTP.

| Компонент | Исходная конфигурация |
|---|---|
| Сайт | Виртуальный хостинг 1Gb.ru, PHP 7.1.33; целевая версия PHP — 7.4 |
| copytrust-svc | VPS Timeweb, Windows Server 2016, Windows Service, WCF self-hosting, .NET Framework 4.7.2 |
| Транспорт | HTTP, `svc2.copytrust.ru:15778` |
| SOAP | HTTP Basic Auth, параметры `TrustSoapClient` |
| Ограничения доступа к API | IP-фильтрация отсутствует |
| Сеть | Публичная сеть; между сайтом и VPS-proxy нет частной сети |
| IP сайта | `81.177.33.25` — указанный адрес; исходящие адреса PHP и VPS-proxy для ACL определяются в Q-06 |

### 1.3. Целевая схема

```text
Клиент 1 — COPYTRUST (PHP 7.4, хостинг 1Gb.ru)
Клиенты 2–5 — другие приложения
                 |
                 | HTTPS / mTLS
                 | индивидуальный сертификат каждого клиента
                 v
+----------------------------------------------------------+
| VPS-proxy — Linux, VPS 1Gb.ru                             |
| HAProxy                                                  |
| - TLS termination и аутентификация клиентов (mTLS)       |
| - реестр разрешённых сертификатов и прав доступа         |
| - сопоставление client_id с учётной записью backend      |
| - Circuit Breaker: health checks, тайм-ауты, fast fail    |
+----------------------------------------------------------+
                 |
                 | HTTPS + Basic Auth (межсервисная)
                 | Windows Firewall: только IP VPS-proxy
                 v
+----------------------------------------------------------+
| VPS Timeweb — Windows Server 2016                        |
| HTTP.sys / WCF / copytrust-svc                            |
| - TLS, существующий механизм идентификации клиентов     |
| - выполнение SOAP / REST операций                       |
+----------------------------------------------------------+

Прямой доступ клиентов к API Timeweb: закрыт.
```

HAProxy располагается на стороне 1Gb.ru, чтобы при отказе межпровайдерского канала сайт мог получить быстрый отказ от VPS-proxy. VPS-proxy является отдельным сервером; его собственная недоступность ограничивается клиентскими тайм-аутами. Дополнительный резервный прокси не предусматривается.

Используется HTTPS (TLS поверх TCP). Имя и порт HTTPS backend задаются по Q-01, публичное имя и порт VPS-proxy — по Q-05. В документе `<BACKEND_HTTPS>` и `<PROXY_HTTPS>` обозначают соответственно полные HTTPS-адреса этих узлов без пути. Внутренняя Basic Auth в схеме — вариант сохранения идентификации клиентов без изменения бизнес-логики; механизм сопоставления и полномочия клиентов фиксируются по Q-12 и Q-13.

## 2. Часть I. Изменения на стороне сайта COPYTRUST

### 2.1. Адреса интеграции

Сохранить существующие имена параметров `.env`. В целевой конфигурации:

```dotenv
SERVICE_PATH=<PROXY_HTTPS>/RegistrationService/2?wsdl
SERVICE_URL=<PROXY_HTTPS>/RegistrationService/2
SERVICE_URI=<PROXY_HTTPS>/RegistrationService/2/ws
SERVICE_REST_URL=<PROXY_HTTPS>/RegistrationService/web/2
```

Это шаблон адресов, а не готовый `.env`; подставить согласованный `<PROXY_HTTPS>`. Состав действующих интерфейсов и назначение `SERVICE_URI` определяются по Q-03. Отдельный endpoint `/RegistrationService/2/ws` в Release-конфигурации WCF не задан. Маршруты, предусмотренные действующим контрактом, включаются в разрешённый набор; остальные не публикуются.

Все обращения, включая WSDL и импортируемые XSD, выполняются через VPS-proxy. `SERVICE_URL` используется как явный `location` SOAP-клиента, чтобы адрес из WSDL не направлял вызовы непосредственно на Timeweb. Для динамического получения metadata публиковать корректные внешние HTTPS-адреса. Выбор между настройкой WCF metadata (включая `useRequestHeadersForMetadataAddress`) и локальным версионируемым комплектом WSDL/XSD с явно заданным `location` определяется по Q-04. После каждого переключения обновить кеш WSDL.

### 2.2. Тайм-ауты

Централизовать настройку тайм-аутов в существующем `TrustSoapClient` на PHP 7.4. Различать время установки соединения и время ожидания данных. Тайм-аут SOAP по умолчанию — существующие 30 секунд; этап 1 его не изменяет.

Для этапа 2 предусмотреть передачу индивидуального тайм-аута SOAP-метода в централизованную обёртку клиента и применение значения по умолчанию при его отсутствии. Значения, перечень методов, место хранения настроек и соотношение клиентских и прокси-тайм-аутов определяются по Q-07. Для используемых REST-вызовов установить аналогичные ограничения с учётом их транспорта.

Тайм-ауты согласовывать по фазам соединения и классам операций. Время подключения HAProxy к backend должно быть существенно меньше допустимого времени ожидания клиента. Если клиент должен получить управляемый HTTP 504 от HAProxy, его бюджет ожидания должен позволять прокси завершить обработку по своему тайм-ауту и передать ответ, с учётом подключения, очереди и сетевых задержек. Если приоритетом конкретного метода является более раннее освобождение обработчика Apache, допустим меньший клиентский тайм-аут; в этом случае клиент обрабатывает собственный тайм-аут, а не ожидает HTTP 504. Универсальное соотношение клиентского тайм-аута и `timeout server` не устанавливается: они могут контролировать разные фазы и виды сетевого ожидания.

В стандартном `SoapClient` PHP 7.4 нет параметра тайм-аута отдельного `__soapCall()`. Предусмотрены два способа реализации: обёртка с временной установкой `default_socket_timeout` и восстановлением значения в `finally` либо переопределение `__doRequest()` с транспортом cURL и `CURLOPT_TIMEOUT_MS`. Первый способ ограничивает сетевое ожидание, но не гарантирует абсолютный дедлайн операции; второй позволяет ограничить полную длительность HTTP-передачи, но требует сохранения поведения SOAP-транспорта, включая Basic Auth, TLS и обработку SOAP Fault. Выбор способа и необходимость жёсткого дедлайна — Q-07. Создание SOAP-клиента и загрузку WSDL также ограничить тайм-аутами.

На уровне приложения не выполнять автоматические повторы операций, изменяющих состояние. При транспортной ошибке, HTTP 503/504 или тайм-ауте завершать обработку зависимой операции с предусмотренной обработкой `SoapFault`. Тайм-аут не доказывает, что операция на backend не была выполнена; повтор возможен только после проверки её результата либо при гарантированной идемпотентности.

### 2.3. HTTPS и клиентская аутентификация

- На этапах 1–2 сохранить действующие `login`/`password` в `TrustSoapClient`; передавать их исключительно по HTTPS.
- На этапе 3 заменить внешнюю Basic Auth на клиентский сертификат. Для `SoapClient` передавать PEM-сертификат и ключ посредством `local_cert`/`local_pk` в `stream_context` либо поддерживаемой опции `local_cert` с объединённым PEM. Если ключ зашифрован, передавать `passphrase` из защищённой конфигурации. Для REST-клиента применить эквивалентную TLS-настройку его транспорта.
- Проверять сертификат узла назначения по доверенному УЦ и DNS-имени (`verify_peer=true`, `verify_peer_name=true`): Timeweb на этапе 1, VPS-proxy на этапах 2–3. Не отключать проверку TLS. На всех участках и этапах применять единую политику TLS, приведённую ниже.
- Хранить закрытый ключ вне web-root и репозитория, с доступом только у учётной записи приложения. Хранить пути к файлам сертификатов и ключей в конфигурации, пароль ключа — в защищённой конфигурации, если он используется. Имена параметров и формат сертификата определяются по Q-14.
- После перехода на mTLS удалить Basic-реквизиты backend из настроек сайта и прекратить их передачу. Каждый новый клиент получает отдельный сертификат и ключ; общие клиентские ключи не допускаются.

**Единая политика TLS для всех межсерверных соединений (этапы 1–3):** минимальная версия — TLS 1.2; TLS 1.3 разрешён при поддержке обеими сторонами. SSL 2.0/3.0 и TLS 1.0/1.1 запрещены. Использовать современные наборы шифров, предпочтительно ECDHE с AES-GCM для TLS 1.2; исключить слабые наборы (в частности NULL, anonymous, EXPORT, RC4, DES/3DES и наборы с MD5). Проверка доверия к серверному сертификату и соответствия имени обязательна. Конкретные наборы и параметры для PHP/OpenSSL, HAProxy и Windows Schannel определяются по Q-02 с учётом совместимости. Проверять фактическое согласование протокола и наборов шифров на каждом участке, а не только наличие настроек.

## 3. Часть II. Конфигурирование copytrust-svc (VPS Timeweb)

### 3.1. HTTPS в WCF / HTTP.sys

В `CTService/CTService.cs` Windows Service запускает `ServiceHost` для SOAP, REST и TextSearch. Приём HTTP(S)-запросов обеспечивает HTTP.sys. Дополнительный IIS или HTTPS reverse proxy на Windows не требуется.

Изменения относятся к конфигурации установленной службы `CTService.exe.config` (шаблон: `CTService/app.Release.config`) и настройкам Windows:

1. Установить серверный TLS-сертификат с SAN, соответствующим согласованному имени HTTPS backend (Q-01, Q-02) и закрытым ключом в `LocalMachine\My`.
2. Зарегистрировать сертификат HTTP.sys для согласованного HTTPS-порта посредством `netsh http add sslcert`; настроить разрешения URL ACL для учётной записи службы. Настроить Windows Schannel согласно единой политике TLS (раздел 2.3, Q-02). Перед изменением системных настроек протоколов и наборов шифров проверить влияние на другие службы Windows; после применения проверить согласование TLS по HTTPS API.
3. Для SOAP изменить `basicHttpBinding` с `TransportCredentialOnly` на `Transport`, сохранив Basic Auth и существующие квоты сообщений:

   ```xml
   <security mode="Transport">
       <transport clientCredentialType="Basic" />
   </security>
   ```

4. Перевести адрес SOAP на `<BACKEND_HTTPS>/RegistrationService/2`, metadata — на `httpsGetEnabled="true"`, MEX — на `mexHttpsBinding`, если используется. Для старых HTTP-адресов отключить публикацию metadata после переключения клиентов.
5. Для REST изменить транспорт `webHttpBinding` на HTTPS (`security mode="Transport"`). На этапе 1 сохранить действующий режим доступа REST: в исходной Release-конфигурации `security mode="None"`. Для REST-операций без транспортной аутентификации использовать HTTPS с `clientCredentialType="None"`; для аутентифицируемых сохранить соответствующий механизм. Состав интерфейсов и действующие правила — Q-03. В целевом состоянии внешняя аутентификация REST выполняется на VPS-proxy; правила авторизации задаются для каждого разрешённого интерфейса.
6. Используемые дополнительные интерфейсы, включая TextSearch, перенести на HTTPS и включить в защищённую маршрутизацию VPS-proxy либо отключить внешний доступ к ним. Не изменять общий `HttpBinding` для одного endpoint без синхронного изменения остальных использующих его адресов; использовать отдельные binding-конфигурации при поэтапном переходе.
7. На этапе 1 перевести требуемые endpoints на HTTPS; способ переключения (параллельные bindings на другом порту или согласованное окно замены на текущем порту) определяется по Q-01. После переключения закрыть внешние HTTP-listeners. На этапе 3 ограничить сетевой доступ к API исключительно VPS-proxy.

Для регистрации сертификата и URLACL применяются штатные команды `netsh http add sslcert`, `netsh http add urlacl`; для инспекции — `netsh http show sslcert`, `netsh http show urlacl`, `netsh http show servicestate`. Привязка сертификата к порту не заменяет настройку WCF binding.

### 3.2. Межсервисная аутентификация и идентификация клиентов

В целевой схеме клиентские сертификаты проверяются на VPS-proxy. Для сохранения существующей бизнес-идентификации предусмотрен вариант внутренней Basic Auth для соединений HAProxy → `copytrust-svc`. Этот механизм не используется внешними клиентами. Окончательное решение о сопоставлении записей и прав — Q-12, Q-13; описание ниже задаёт реализацию данного варианта.

Для каждого клиента создаётся или сохраняется соответствующая запись клиента в `copytrust-svc`. Реквизиты этой записи используются исключительно VPS-proxy. Не использовать одну общую Basic-учётную запись для всех клиентов: в `RegistrationService/RegistrationService.cs`, методе `SubmitRegistrationTask`, имя из `ServiceSecurityContext.Current.PrimaryIdentity.Name` применяется для получения `ClientInfo` и установки `info.ClientID`. Индивидуальное соответствие сохраняет принадлежность регистраций и действующую бизнес-логику.

На этапе 3 сменить пароли backend-учётных записей, ранее хранившиеся у клиентов. Управление внешним доступом выполняется на VPS-proxy, бизнес-идентификация и существующие ограничения операций остаются в `copytrust-svc`. Замена валидатора WCF на собственный протокол доверенных заголовков не требуется.

### 3.3. Ограничение прямого доступа

На этапе 3 настроить Windows Firewall и, при наличии, сетевой firewall Timeweb:

| Входящий трафик | Правило |
|---|---|
| Согласованный TCP-порт (HTTPS API) | Разрешить только с согласованных фиксированных исходящих IPv4/IPv6-адресов VPS-proxy; внешний доступ по другим адресам и неиспользуемому семейству IP закрыть |
| Старый HTTP API (исходный TCP 15778) | Запретить внешний HTTP-доступ; удалить неиспользуемые HTTP-listeners. Если порт повторно используется для HTTPS, применить правило HTTPS API |
| Другие порты API, в том числе TextSearch | Перенести за VPS-proxy либо закрыть внешний доступ |
| RDP / администрирование | Только отдельные административные правила; не через публичный API |

Проверить IPv4 и IPv6, удалить широкие разрешающие правила. Список адресов и порядок переключения — Q-06 и Q-15. Перед закрытием доступа перенести всех действующих клиентов API, включая интеграции с legacy-адресами, если они используются. В частности, в `CTPartnerService/app.Release.config` есть клиентский адрес `/RegistrationService` на порту 15778; этот маршрут должен быть мигрирован или выведен из эксплуатации вместе с другими прямыми вызовами.

### 3.4. Защита секретов и журналов

До завершения внедрения исправить `CustomUserNamePasswordValidator.Validate()` в `RegistrationService/RegistrationService.cs`: исключить переданный пароль из сообщений об ошибках. Ограничить доступ к существующим журналам и провести ротацию затронутых реквизитов. Отключить раскрытие внутренних деталей исключений через WCF `includeExceptionDetailInFaults` на production, сохранив предусмотренные контрактом SOAP Fault.

Удалить AWS-ключи из отслеживаемой Release-конфигурации и заменить соответствующие действующие ключи; хранить секреты вне репозитория. Эти работы являются самостоятельными мерами безопасности, выполняемыми после срочного переключения HTTPS, а не дополнительным условием этапа 1.

## 4. Часть III. Настройка VPS-proxy (1Gb.ru)

### 4.1. Компоненты и TLS

На Linux VPS установить поддерживаемую LTS-версию HAProxy. Версия, ОС, способ установки и конфигурация ресурсов определяются по Q-05. Запуск — штатная системная служба. После инициализации HAProxy выполняет обработку запросов от отдельной непривилегированной учётной записи с минимально необходимыми правами. HAProxy работает в HTTP mode, завершает входящее TLS-соединение и устанавливает отдельное TLS-соединение до WCF. Дополнительный HTTP-сервер, Vault и служба выдачи сертификатов на VPS не требуются.

- Frontend: `<PROXY_HTTPS>`, серверный сертификат с SAN для выбранного имени, TLS согласно единой политике раздела 2.3 (Q-05, Q-02).
- Backend: `<BACKEND_HTTPS>`, `ssl verify required`, доверенный CA, явная проверка согласованного DNS-имени (`verifyhost`) и SNI для рабочих запросов и health checks. HTTP Host формируется в соответствии с адресацией WCF и правилами публикации metadata. Запретить `verify none`. Для исходящего TLS также применять политику раздела 2.3; проверять настройки обоих направлений отдельно.
- Разрешить только целевые Host, методы и маршруты API. Не реализовывать произвольное HTTP-проксирование; не принимать CONNECT, произвольные host/path и доверенные идентификационные заголовки от клиентов.
- На этапе 2 ограничить входящий доступ по фактическому стабильному egress IP сайта, когда это возможно; при общем IP хостинга полагаться также на Basic Auth. На этапе 3 mTLS обязателен для всех клиентских маршрутов, IP ACL применяется как дополнительная защита при наличии стабильных адресов клиентов.
- Административный интерфейс, Runtime API (stats socket) и SSH доступны только администраторам. Runtime API не публиковать в сеть; локальный сокет защитить правами файловой системы. Доступ к командам просмотра map-файлов (в том числе `show map`) и изменения состояния прокси предоставлять только уполномоченным администраторам, поскольку map может содержать секреты. HTTP-порт 80 API не обслуживает; если выбран публичный УЦ, способ прохождения ACME challenge определяется по Q-02.

### 4.2. Circuit Breaker

HAProxy использует активные health checks, исключение недоступного backend и ограниченные сетевые тайм-ауты. Механизм единый для всех клиентов; отдельного хранилища состояния не требуется.

| Состояние | Поведение |
|---|---|
| UP | Авторизованные запросы передаются `copytrust-svc` |
| DOWN | Новые авторизованные запросы немедленно получают HTTP 503, без обращения к backend |
| Восстановление | После заданного числа успешных проверок HAProxy автоматически возвращает backend в UP |

Параметры HAProxy определяются в Q-07 и Q-08:

| Директива / параметр | Требование |
|---|---|
| `timeout connect` | Ограниченное время подключения к backend |
| `timeout server` | Ограниченное сетевое бездействие при обслуживании запроса |
| `timeout client` | Согласовать с клиентскими тайм-аутами и допустимой передачей данных |
| `timeout http-request` | Ограничить время получения HTTP-заголовков |
| `timeout queue` | Ограничить ожидание в очереди при её наличии |
| `timeout check`, `inter`, `fall`, `rise` | Определить допустимое время обнаружения отказа и восстановления |
| `retries` | 0; без автоматических повторов изменяющих операций |
| `maxconn` / лимиты очереди | Решение и значения по Q-10 |

`timeout server` — тайм-аут сетевого бездействия. До получения ответа при истечении тайм-аута HAProxy возвращает 504; если ответ уже начат, соединение может быть прервано. Не считать эти значения жёстким дедлайном всей операции. Индивидуальные прикладные тайм-ауты задаёт сайт. При выборе значений учитывать совместный бюджет подключения, очереди, ожидания ответа и передачи ошибки клиенту; применять принципы раздела 2.2 (Q-07).

**Проверка работоспособности:** активный HTTPS health check должен выявлять не только сетевой отказ, но и отсутствие корректного ответа приложения. Проверка выполняется с конечным тайм-аутом, без бизнес-операций, изменения состояния бизнес-данных или иных прикладных побочных эффектов; допустимо техническое журналирование. Проверка должна быть лёгкой и не зависеть от произвольных бизнес-данных. Критические зависимости (включая БД, если её отказ делает основные операции невозможными) включаются в проверку только по согласованному контракту готовности.

Для проверки предусмотрено использование существующей SOAP-операции `IRegistrationService.Test` (контракт `CopyTrustServiceLibrary/IRegistrationService.cs`, реализация `RegistrationService/RegistrationService.cs`) либо иного согласованного диагностического контракта (Q-09). Определить корректный запрос и проверяемые признаки успешного SOAP-ответа, реквизиты технического клиента, зависимости всего пути выполнения, включая аутентификацию, и стоимость проверки. HTTP 200 без ожидаемого ответа, как и наличие TCP/TLS-соединения, сами по себе не являются достаточной проверкой приложения. Отдельные liveness/readiness endpoints не требуются.

Пассивное наблюдение за транспортными ошибками (`observe layer4`) — дополнительный вариант ускорения отключения (Q-08). Не отключать backend по любому HTTP 500: WCF может возвращать таким статусом штатный SOAP Fault. Активная проверка и тайм-ауты являются базовым механизмом.

При отказе уже выполняющиеся запросы освобождаются по своим тайм-аутам; новые запросы после DOWN отклоняются сразу. При внезапном отказе до перехода DOWN и при недоступности самого VPS-proxy остаётся окно ожидания; его ограничивают тайм-ауты сайта. Архитектура не гарантирует абсолютного отсутствия очередей при произвольной нагрузке.

### 4.3. Аутентификация клиентских приложений (целевой этап 3)

Для 2–5 клиентов используется **mTLS + файловый реестр сертификатов HAProxy**, без отдельной БД или сервера управления секретами.

**Удостоверяющий центр.** Для малой клиентской базы использовать собственный клиентский CA без постоянно работающего сервера PKI. Корневой сертификат является самоподписанным, CA подписывает индивидуальные клиентские сертификаты с `Extended Key Usage = clientAuth`. Закрытый ключ CA хранится вне VPS, в зашифрованном виде, с резервной копией. Инструмент выпуска (например, OpenSSL), место выполнения операций, сроки сертификатов и регламент ротации определяются по Q-11.

Серверные TLS-сертификаты VPS-proxy и Timeweb выпускаются выбранным публичным УЦ либо отдельным собственным серверным CA (Q-02). При собственном CA корневой сертификат добавляется в доверенные хранилища соответствующих клиентов. Не использовать клиентский CA как универсальный доверенный серверный CA. Для Windows серверный сертификат и ключ импортируются в системное хранилище, при необходимости в PKCS#12. Отдельный постоянно работающий УЦ не нужен.

**Проверка клиента:**

1. HAProxy предъявляет собственный серверный сертификат. Клиент проверяет его цепочку и имя.
2. HAProxy требует клиентский сертификат (`bind ... ssl crt ... ca-file ... verify required`), проверяет его цепочку, срок действия и допустимость для клиентской аутентификации.
3. Из сертификата вычисляется SHA-256 отпечаток DER. По точному совпадению отпечатка с записью локального map-файла определяется внутренний `client_id`. Доверия к CA недостаточно: сертификаты вне реестра отклоняются (HTTP 403); отсутствующие или невалидные сертификаты отклоняются на TLS-рукопожатии.
4. Проверяются разрешённые для `client_id` маршруты API и, когда это требуется матрицей прав Q-13, SOAP-операции. Неизвестные или запрещённые маршруты не передаются backend. Если авторизация по операциям уже выполняется backend, она сохраняется; путь SOAP endpoint сам по себе не различает методы SOAP.
5. HAProxy удаляет все полученные от клиента заголовки `Authorization` и заголовки идентификации, затем устанавливает собственный `Authorization: Basic ...` для соответствующей внутренней записи `copytrust-svc`. Для маршрута, требующего внутренней Basic Auth, при отсутствии или непригодности соответствующих backend-реквизитов запрос отклоняется на прокси без обращения к backend; использование чужих или общих реквизитов по умолчанию запрещено. Для интерфейсов без Basic Auth применяется их согласованный backend-контракт; клиентская mTLS обязательна независимо от него.
6. Клиенту возвращается ответ `copytrust-svc` без изменения SOAP-контракта. Если backend DOWN, разрешённый запрос получает быстрый 503.

Пример структуры локальных файлов (идентификаторы условные, секреты и реальные отпечатки не приведены):

| Файл | Содержание |
|---|---|
| `/etc/haproxy/pki/client-ca.crt` | Публичный корневой сертификат клиентского CA |
| `/etc/haproxy/pki/server.pem` | Сертификат и закрытый ключ VPS-proxy |
| `/etc/haproxy/maps/clients.map` | `sha256_отпечаток client_id` |
| `/etc/haproxy/maps/backend-auth.map` | `client_id Basic_credential` (секрет; значение для формирования Basic Auth) |
| `/etc/haproxy/maps/client-access.map` | Разрешённые группы маршрутов по client_id; ACL deny-by-default |
| Защищённый конфигурационный файл HAProxy | Параметры backend, включая секрет диагностической учётной записи |

Пример реестра `clients.map`:

```text
<SHA256_CERT_COPYTRUST> client-copytrust
<SHA256_CERT_CLIENT_02> client-02
```

Формат отпечатка стандартизировать как 64 строчных шестнадцатеричных символа без разделителей. В выбранной версии HAProxy использовать вычисление отпечатка сертификата и преобразование в hex с тем же форматом. Не принимать `client_id` из HTTP-заголовка, параметра URL или SOAP-тела.

Реквизиты в `backend-auth.map` — секреты, Base64 не является шифрованием. Хранить файл и закрытые ключи с минимальными правами (например, 0600 у root при загрузке HAProxy от root; при иной модели запуска — только необходимые права службы). Не помещать их в Git, общие каталоги и обычные журналы/резервные копии. Резервные копии секретов — зашифрованные, с ограниченным доступом. Для 2–5 клиентов достаточно локального хранения с доступом администратора; отдельный Vault не нужен.

### 4.4. Эксплуатация сертификатов и клиентов

| Процесс | Действия администратора |
|---|---|
| Подключить клиента | Создать запись/права в copytrust-svc; клиент генерирует ключ и CSR; подписать CSR в собственном CA; добавить отпечаток, client_id и внутренние Basic-реквизиты в map; передать публичный сертификат и цепочку клиенту |
| Продлить сертификат | Выпустить новый сертификат, временно добавить второй отпечаток того же client_id, переключить клиента, удалить прежний отпечаток |
| Отключить клиента / компрометация ключа | Удалить все соответствующие отпечатки из реестра, применить конфигурацию, завершить уже открытые сессии клиента (при необходимости принудительно завершить старые HAProxy workers), отозвать сертификат в CA; сменить внутренний пароль при компрометации реквизитов |
| Ротация backend-пароля | Согласованно обновить запись copytrust-svc и закрытый map на VPS-proxy; не передавать пароль клиенту |
| Ротация серверных сертификатов | Обновить сертификат, ключ и необходимые цепочки доверия до истечения срока, применить конфигурацию и проверить оба HTTPS-участка |

Для малой клиентской базы allowlist по отпечаткам является механизмом оперативного отзыва доступа. Ведение CRL допустимо как дополнительная мера. При обновлении реестра подготавливать согласованный комплект файлов, выполнять атомарную замену каждого файла, проверку `haproxy -c -f /etc/haproxy/haproxy.cfg`, затем управляемый reload; при ошибке проверки не применять изменения и восстановить предыдущий согласованный комплект. Не допускать параллельного изменения файлов во время применения комплекта.

Различать два режима применения конфигурации:

- Обычное обновление: graceful reload, без принудительного завершения всех старых процессов при каждом изменении.
- Срочный отзыв доступа: применить исключение клиента из реестра и в пределах согласованного времени (Q-11) гарантированно прекратить его доступ через новые и уже установленные соединения, включая возобновлённые TLS-сессии. При необходимости принудительно завершить старые процессы и активные соединения (в том числе с использованием `hard-stop-after`, если применимо); при невозможности избирательного прекращения доступа допускается контролируемый перезапуск HAProxy. Механизм применения должен исключить обход обновлённого реестра посредством TLS session resumption. Проверить фактический отказ отозванному клиенту, а не только успешность reload.

Контроль сроков сертификатов — эксплуатационная обязанность администратора (без отдельной системы мониторинга).

### 4.5. Журналирование

HAProxy регистрирует время запроса, внутренний `client_id` после mTLS, разрешённый маршрут без секретных query-параметров, статус HTTP, длительность, сетевую ошибку, переходы UP/DOWN. Не регистрировать заголовок `Authorization`, SOAP-тело, приватные ключи, пароли и содержимое документов. Ограничить доступ к журналам и настроить ротацию с двумя обязательными конфигурируемыми ограничениями: максимальным сроком хранения и максимальным суммарным объёмом журналов (включая ротированные файлы). Значения и способ ротации — Q-05, исходя из эксплуатационной необходимости и ресурсов VPS. Отдельная система журналирования не требуется. Проверки доступности не инициируют пользовательские операции.

## 5. План внедрения (три этапа)

Этапы выполняются строго последовательно. После каждого этапа сохраняется работоспособная конфигурация. Изменения этапов 2–3 не включаются в срочное переключение этапа 1. Перед каждым этапом закрыть обязательные для него вопросы из раздела 6; решения отразить в соответствующих частях SAD. Состав работ и критерии ниже описывают целевое поведение, а не готовые команды развёртывания.

### Этап 1. Срочное закрытие HTTP-канала: HTTP → HTTPS

**Цель:** обеспечить шифрование действующего прямого соединения сайта с `copytrust-svc`, ничего не меняя в механизме аутентификации и бизнес-логике.

```text
COPYTRUST -- HTTPS + существующий Basic Auth --> copytrust-svc
```

Работы:

1. Выпустить серверный сертификат для `svc2.copytrust.ru` и настроить доверие PHP.
2. Настроить HTTPS в WCF/HTTP.sys (раздел 3.1), сохранив существующие SOAP/REST контракты и режимы авторизации; переключить endpoints способом, выбранным по Q-01.
3. Переключить все действующие URL сайта на `<BACKEND_HTTPS>/...`, сохранив пути и имена переменных `.env`; обновить WSDL-кеш, проверить импортируемые схемы и другие действующие клиенты.
4. После успешной проверки закрыть наружный HTTP-доступ к API; остальные используемые HTTP-клиенты предварительно перевести на HTTPS.

**Критерий завершения:** все используемые операции работают по прямому HTTPS с проверкой серверного сертификата; недоверенный/просроченный сертификат или сертификат с неподходящим именем отклоняется; соблюдается политика TLS раздела 2.3; публичный HTTP API закрыт. Basic Auth, SOAP-тайм-аут 30 секунд и логика приложения сохранены. HAProxy, mTLS, индивидуальные тайм-ауты и изменение клиентской авторизации не внедряются.

### Этап 2. Введение VPS-proxy и Circuit Breaker

**Цель:** изолировать сайт от сетевых отказов `copytrust-svc`, сохранив существующую клиентскую Basic Auth на backend.

```text
COPYTRUST -- HTTPS + Basic Auth --> HAProxy -- HTTPS + Basic Auth --> copytrust-svc
```

Работы:

1. Развернуть VPS-proxy на 1Gb.ru, настроить DNS, серверный TLS-сертификат и защищённый HTTPS backend.
2. Настроить HAProxy, health checks, Circuit Breaker, тайм-ауты, журналирование и допустимые маршруты (разделы 4.1, 4.2, 4.5). Не включать mTLS, не хранить клиентские backend-пароли в map: исходный Basic `Authorization` передаётся в `copytrust-svc` без изменения. Секрет технической health-проверки хранится отдельно.
3. Переключить адреса `.env` сайта на VPS-proxy. Устранить обход через WSDL и проверить все необходимые SOAP/REST маршруты.
4. В `TrustSoapClient` на PHP 7.4 реализовать централизованную настройку индивидуальных тайм-аутов и корректный быстрый выход при транспортных ошибках (раздел 2.2). Существующие 30 секунд — значение по умолчанию, пока не назначены тайм-ауты конкретных методов.
5. Проверить сетевые отказы и восстановление без перезапуска Apache; выполнить самостоятельные меры защиты секретов и журналов из раздела 3.4.

**Критерий завершения:** при недоступности Timeweb HAProxy переходит в DOWN, быстро отклоняет новые запросы и автоматически возвращает UP после восстановления. PHP освобождает обработчики в пределах настроенных ограничений сетевого ожидания; нет автоматических повторов изменяющих операций. При штатной работе сохраняются SOAP-результаты и клиентские идентификаторы. При согласованной расчётной нагрузке выполнены количественные критерии защиты Apache по Q-10 и разделу 7. Прямой HTTPS API Timeweb временно сохраняется для переходного периода и отката; HTTP закрыт с этапа 1.

### Этап 3. Централизация аутентификации и закрытие обхода VPS-proxy

**Цель:** аутентифицировать всех внешних клиентов на VPS-proxy по индивидуальным сертификатам, исключить прямые вызовы API.

```text
Клиенты 1–5 -- HTTPS/mTLS --> HAProxy -- HTTPS/внутренний Basic Auth --> copytrust-svc
```

Работы:

1. Создать клиентский CA и выдать индивидуальные сертификаты клиентам. Создать map-файлы сертификатов, прав и backend-реквизитов по разделу 4.3.
2. Настроить mTLS и точный allowlist отпечатков. При миграции использовать способ переключения по Q-15 (временный HTTPS frontend для mTLS либо согласованное окно); не оставлять Basic-only frontend в целевой конфигурации.
3. Перевести `TrustSoapClient` и другие клиентские приложения на сертификаты. Для каждого клиента проверить идентификацию, разрешённые маршруты и сохранение `ClientID` в `copytrust-svc`.
4. Сменить прежние backend-пароли и сохранить новые только на VPS-proxy и в `copytrust-svc`. Удалить прежние Basic-секреты из систем клиентов. На VPS-proxy устанавливать `Authorization` только согласно проверенному сертификату.
5. Закрыть прямой внешний доступ ко всем API Timeweb (раздел 3.3). Удалить переходные frontends и правила, допускающие внешние вызовы без mTLS.
6. Отработать выпуск, продление и срочный отзыв сертификата, обновление конфигурации и восстановление из защищённой резервной копии.

**Критерий завершения:** каждый зарегистрированный клиент работает только через VPS-proxy и под своим `ClientID`; запросы без сертификата, с незарегистрированным/просроченным/отозванным сертификатом или с запрещённым маршрутом отклоняются; прямое соединение с API Timeweb с адресов клиентов недоступно по IPv4/IPv6.

**Обязательная проверка изоляции идентификации:** при предъявлении сертификата клиента А и Basic-реквизитов клиента Б во входящем `Authorization` запрос идентифицируется в `copytrust-svc` только как клиент А, если операция разрешена А. При отсутствии backend-реквизитов А для маршрута с внутренней Basic Auth запрос отклоняется на HAProxy без передачи backend. Срочный отзыв прекращает доступ через новые, существующие и возобновлённые TLS-сессии в пределах времени по Q-11.

## 7. Приёмочные проверки и откат

| Проверка | Этап | Ожидаемый результат |
|---|---:|---|
| Валидный / невалидный серверный сертификат | 1, 2, 3 | Штатный вызов / отказ TLS соответственно, включая проверку имени и доверия |
| Версии TLS и наборы шифров на всех действующих участках | 1–3 | Согласуются только протоколы и наборы, разрешённые политикой раздела 2.3 и Q-02; устаревшие протоколы и запрещённые наборы отклоняются |
| HTTP API Timeweb | 1–3 | Внешний доступ закрыт после этапа 1 |
| SOAP, WSDL/XSD, REST и дополнительные используемые интерфейсы | 1–3 | Работают предусмотренные операции; нет обхода целевого маршрута |
| Остановка WCF, блокировка межсерверного TCP, нарушение TLS | 2–3 | Backend DOWN, новые запросы получают 503, штатное восстановление UP |
| Открытый порт при отсутствии SOAP-ответа | 2–3 | Неуспешная рабочая health-проверка, ограниченное ожидание |
| Штатный SOAP Fault, длительная операция, передача больших данных | 2–3 | Нет ошибочного отключения backend по бизнес-Fault; корректные тайм-ауты и результаты |
| Недоступность самого VPS-proxy | 2–3 | Сайт завершает зависимые операции по собственным сетевым тайм-аутам |
| Нагрузка при отказе backend | 2–3 | При согласованной расчётной нагрузке выполнены количественные критерии ниже; независимые от `copytrust-svc` страницы сохраняют доступность |
| Клиентские сертификаты и подмена Authorization | 3 | Допуск только по реестру; сертификат А с внешними Basic-реквизитами Б идентифицируется как А при разрешённом вызове; при отсутствии внутренних реквизитов для обязательной Basic Auth — отказ на прокси без вызова backend |
| Ротация/отзыв, прямые обращения по IPv4/IPv6 | 3 | Новый сертификат работает; прямой обход API заблокирован по обоим семействам IP; после срочного отзыва новые, уже установленные соединения и возобновлённые TLS-сессии отозванного клиента не дают доступа в пределах времени по Q-11 |

**Количественная проверка защиты Apache (этапы 2–3).** Значения ниже согласуются в Q-10, а T-down — совместно с Q-08. Испытание проводится при расчётной нагрузке, включая зависимые и независимые от backend HTTP-запросы.

| Показатель | Критерий |
|---|---|
| RPS | Согласованная интенсивность тестовой нагрузки, с заданным составом запросов и параллелизмом |
| T-down | Максимальное время от искусственного отказа backend до состояния DOWN в HAProxy |
| T-fail | Максимальное время ответа сайта на новые зависимые запросы после DOWN; отдельно контролировать быстрый HTTP 503 от HAProxy |
| T-recovery | Максимальное время от DOWN до освобождения ранее занятых ожиданием backend обработчиков Apache и восстановления согласованного уровня занятости |
| N-workers | Максимально допустимое число одновременно занятых рабочих процессов Apache после T-recovery в течение согласованного окна наблюдения; порог ниже действующего лимита 20 |

В ходе проверки фиксировать все показатели и проверять доступность независимых страниц сайта в пределах согласованного критерия задержки/ошибок. Повторить проверку для сетевой недоступности и доступного TCP/TLS-порта без корректного SOAP-ответа; отдельно проверить восстановление UP в пределах времени по Q-08. Способ измерения занятых, а не просто существующих процессов Apache, определить до испытания в Q-10 (например, доступный только администраторам `mod_status` либо эквивалентный источник). Критерии относятся к согласованной нагрузке, а не произвольному потоку запросов.

Откат выполняется к последнему успешно завершённому этапу: этап 2 — к прямому HTTPS; этап 3 — к защищённому HTTPS через HAProxy с предыдущим механизмом Basic Auth, с контролируемым восстановлением соответствующих реквизитов и правил доступа. Для срочного этапа 1 допускается временное сохранение HTTP только во время контролируемого окна переключения; возврат к открытому HTTP с Basic Auth не является штатным вариантом эксплуатации. При невозможности безопасного отката операция остаётся временно недоступной до восстановления защищённого доступа.
